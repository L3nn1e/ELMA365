# Разбор elma365-backupper 1.0.18 для нашей установки

Разобран `/opt/elma365/backupper/bin/elma365-backupper` (2398 строк, прислал Lenny 2026-10-11) применительно к нашей схеме: ELMA в Deckhouse (dev `elma365`, prod `mscelma365`), PostgreSQL, MongoDB и MinIO внешние на elma-backend. Номера строк ниже указаны по этому файлу.

## Итог

- **Бэкап (`backup all`) данные не портит.** Он только читает: `pg_dump` (стр. 1221), `mongodump` (1470) и `mcc mirror` из бакета ELMA в новую локальную папку (1208). Ключ `--remove` у mirror относится к папке копии, а не к бакету.
- **Уронить он может доступность, а не данные:** переполнить корень мастера Kubernetes, оставить ELMA в 0 реплик при обрыве, сбросить реплики, разбудить ELMA в окно снапшотов. Всё это закрывает обёртка [elma-backupper-run.sh](../scripts/elma-backupper/elma-backupper-run.sh), её надо ставить вместе с бэкапером.
- **Восстановление с `--cleanup-databases` разрушительно и местами грубое.** Запускать его только после свежего ZFS-снапшота на elma-backend (`elma-backup.sh -e <env>`): это настоящая страховка.

## Восстановление: что делает `--cleanup-databases`

- **PostgreSQL** (1553–1607). Для каждой компании из `public.companies` выполняется `DROP SCHEMA … CASCADE`, затем `DROP TABLE` каждой таблицы `public` (без CASCADE), затем `DROP SEQUENCE` всех последовательностей по имени. Функции, типы, представления и расширения не удаляются.
  - Если таблицу держит представление, `DROP TABLE` падает, скрипт уходит в `error_exit`, и тот **поднимает ELMA на полуочищенной базе** (1051).
  - Оставшиеся объекты дают при `pg_restore` ошибки «already exists». Скрипт считает успехом любой вывод со строкой `errors ignored on restore` (1376), поэтому настоящая ошибка восстановления может пройти незамеченной.
- **MongoDB** (1543): удаляет все коллекции базы из `MONGO_URL`, кроме `system.*`. Это ожидаемо.
- **Порядок `restore all`**: сначала MongoDB (ELMA в 0), потом PostgreSQL, потом `scale_1`, и только **после этого** S3 (`mcc mirror --remove` в боевой бакет, 2133–2135). Пока зеркалится MinIO, ELMA уже работает: файлы, которые пользователи загрузят в эти минуты, будут удалены, а часть старых ссылок какое-то время не откроется.
- Любая ошибка посреди восстановления приводит к `error_exit` и `scale_1`, то есть ELMA стартует на частично восстановленных данных.
- Без `--backup-path` скрипт спрашивает подтверждение с клавиатуры (1422). Путь всегда указывать явно.

**Порядок безопасного восстановления:**
1. На elma-backend выполнить `elma-backup.sh -e <env>`. Это свежий консистентный ZFS-снапшот, точка возврата.
2. На deckhouse-master: `elma365-backupper restore all --config <конфиг env> --backup-path <копия>/ --cleanup-databases`.
3. Проверить ELMA. Если что-то не так, откатиться снапшотом через `elma-restore.sh -e <env>`.

Первый раз только на dev, днём, по плану учений в треде.

## Установка обёртки (deckhouse-master, root)

Сначала нужен диск под копии (предлагается 400 ГБ). Копии ложатся в `/var/storage/backup/dev/` и `/var/storage/backup/prod/` (решение Lenny 2026-10-12), временные папки `/var/storage/backup/<env>/tmp/` у каждого окружения свои и на том же диске, чтобы готовый дамп переносился в копию мгновенно, без второго копирования. Затем:

```sh
df -h /var/storage/backup        # должен быть отдельный диск, не /
mkdir -p /var/storage/backup/{dev,prod}/tmp
cd /opt/elma365/backupper/etc
cp -a config config.orig
for e in dev prod; do
  ns=elma365; [ $e = prod ] && ns=mscelma365
  sed -e "s|^KUBECONFIG=.*|KUBECONFIG=\"/etc/kubernetes/admin.conf\"|" \
      -e "s|^K8S_NS_APP=.*|K8S_NS_APP=$ns|" \
      -e "s|^STORAGE_PATH=.*|STORAGE_PATH=\"/var/storage/backup/$e/\"|" \
      -e "s|^TMP_DIR=.*|TMP_DIR=\"/var/storage/backup/$e/tmp/\"|" config.orig > config-$e
  chmod 600 config-$e
done
grep -E '^(KUBECONFIG|K8S_NS_APP|STORAGE_PATH|TMP_DIR|BACKUP_LIFE)=' config-dev config-prod
```

Дальше установка юнита и таймеров systemd по [README](../scripts/elma-backupper/README.md): `elma-backupper@.service`, `elma-backupper-prod.timer` (23:30) и `elma-backupper-dev.timer` (23:30:30, ждёт prod); всё должно закончиться к 00:55, иначе обёртка прерывает бэкап. Сначала прогон `-n` через `systemd-run`, затем боевой прогон dev днём через `systemctl start elma-backupper@dev`, и только потом `systemctl enable --now` для таймеров. Лог: `journalctl -u elma-backupper@<env>` и `/var/log/elma-backupper-<env>.log`.

Обёртка проверена на заглушках kubectl и бэкапера: успех со сбросом реплик в 1, ошибка, таймаут, спящая ELMA, состояние elma-sleep `activating`, чужой namespace в конфиге, вырезание паролей. Первый боевой прогон на сервере: dev 2026-10-12 12:17–12:22 MSK через `systemctl start elma-backupper@dev`, rc=0, бэкапер 290 с, копия `ELMA365_2026.10.12-12.17.45` (mongo 1.2M, postgres 252M, s3 150M), реплики вернулись как были. Сверка с живой базой: в дампе 3196 таблиц с данными, ровно столько пользовательских таблиц в базе (3264 минус 68 системных), дамп полный.
